## 3. Phase 2 fail analysis

**Pair 14** (the failing case):
- `current_turn_summary` : "Implementing payment processing with Stripe"
- `new_prompt` : "Also support PayPal"
- `label` (Stéphane) : `consult`, recommendation `queue`
- Haiku verdict : `still_useful` — "PayPal support is an additive feature
  request; Stripe work isn't invalidated."

Why Haiku doesn't return `uncertain` here: the prompt's "Also" framing is
genuinely additive language. Without context about whether PayPal would
require ripping out the in-flight Stripe SDK choices, "additive" is the
defensible read. The human label `consult` reflects "this MIGHT also affect
the in-flight architecture choices", which Haiku didn't infer.

**Pair 15** (passed): "I'm not sure if this is the right direction" did
trigger `uncertain` correctly — the explicit hedge was a stronger signal.

**Calibration options for Stéphane** (none applied — strict stop):
1. Tune the classifier prompt to be more conservative (treat 60–80%
   confidence as `uncertain`).
2. Add a second check: if the new prompt mentions a technology adjacent to
   the in-flight work, escalate to `uncertain`.
3. Adjust the human label on pair 14 to `queue` (Haiku's read is reasonable).
4. Accept the recall/precision-only criterion (drop the binary CONSULT
   detection requirement on a 2-pair sample) and replace with a larger
   multi-pair fixture so CONSULT recall/precision can have thresholds too.

I did NOT pick any of these — fitting to the test would invalidate the
fixture's validation purpose.
