
Env knobs : `FAKE_CLAUDE_LATENCY_MS`, `FAKE_CLAUDE_TURN_BUDGET_MS`,
`FAKE_CLAUDE_FAIL_RATE`, `FAKE_CLAUDE_TOOL_USES`. All optional.

### 4.B.2 latency failure analysis

Each "turn" in the test is a fresh `node fake_claude.mjs ...` spawn.
On Windows + Node 24, **node process startup alone takes ~1–1.5 s**
before `fake_claude.mjs` even runs its first line of code. With
`FAKE_CLAUDE_LATENCY_MS=50` (default), the script's own work is
~250 ms, but total wall-clock per turn = startup + work +
exit-flush, which lands at ~1.9 s avg on this hardware.

Measured :
```
n=10  avg=1920 ms  max=4233 ms  (cap = 500 ms per spec)
```

The 500 ms cap is **structurally unachievable** for a Node-based
per-turn-spawned harness on Windows. Two ways forward (none applied
in this run) :

1. **Revise the cap.** A 2 s fake-claude is still 5–30× faster than
   real claude turns ; for the purposes of orchestrator-overhead
   measurement, a 3-s cap would be defensible. (Test 1.3 has
   precedent for accepting a calibration revision.)
2. **Re-architect the harness.** Replace `node fake_claude.mjs` with
   a long-running daemon plus a thin client (e.g., `fake_claude`
   binary that talks to a unix socket / named pipe). Eliminates
   per-turn startup. Significantly more code.
